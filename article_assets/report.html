What the FHIR

I sent 74 plain GET requests to two public FHIR test servers and read the raw JSON that came back. This page shows what they returned, built entirely from those cached responses.

SMARTr4.smarthealthit.org HAPIhapi.fhir.org/baseR4

Counts are from what we fetched, not server totals. * means the search hit our 20-page cap, so more results exist. Each row is its own search, so rows are not subsets of one another.

This page is a snapshot. It shows what the two servers returned on and never contacts them again. Both are public test servers whose data changes, so today's numbers, records and IDs may differ. See Limitations for how to rebuild it.

How we asked

Every request, in order

FHIR is a REST API. A search is a URL: the path names a resource type such as Patient, and the query string holds search parameters. Public test servers are shared, so every request followed the same rules.

  • GET onlyNothing was created, changed or deleted.
  • _count=50Small pages of 50 results.
  • 20 pages maxA hard cap per search, at most 1,000 results.
  • 1 s sleep · 30 s timeoutA pause before every request.
  • cache/Every response saved, so reruns never hit the server.
Click a request to see its full URL.

GET /metadata

Ask the server what it can do

Every FHIR server describes itself in a CapabilityStatement: the FHIR version it speaks, the resource types it holds, and the search parameters it accepts for each one. Search parameters are the names you may put in a query string. They are not the same as the fields in the JSON.

    GET /Condition?code=http://snomed.info/sct|44054006
    
      
    Search by code, never by label
    
    
    
    
    
      
    A token search has the form system|code. The system says which code system you mean (here SNOMED CT) and the code is the concept: 44054006, type 2 diabetes. Each coding also carries a display text for humans. The chart counts the display strings that came back with this one code.
    
    
    
    
    
    
    
      
    
      
    
    
    
    
    
  
    

  
    
    
    
      
    GET /Observation?code=http://loinc.org|4548-4
    
      
    HbA1c, and where to draw the line
    
    
    
    
    
      
    HbA1c measures average blood sugar over about three months, as the percentage of hemoglobin with sugar attached. 6.5% or higher is the usual diagnostic threshold for diabetes. Readings arrive as a valueQuantity: a number plus a unit. Move the threshold to see how many patients cross it.
    
    
    
    
    
      
      
      
    
    
    
    
    
    
    
      
    The same unit can be written several ways. unit is a free-text label for people. system and code are the machine-readable UCUM version, and uploaders fill in either, both or neither.

    HAPI, the public sandbox
    
      
    Five records that should not exist
    
    
    
    
    
      
    HAPI lets anyone write to it, so its data includes test scripts, typos and jokes. The server can find odd records for you: :missing=true finds resources without a field, and prefixes like gt and lt compare dates.
    
    
    
    
    
    
    
      
    The weird thing that wasn't
    
      
    I expected references to patients that don't exist. I looked up 1,000 of the 1,031 patients referenced by diabetes Conditions and HbA1c Observations, 50 at a time with Patient?_id=a,b,c…, and every one of them exists. HAPI rejects a write that points to a missing patient. It does not reject a missing required field or an impossible date, so it checks the links between records but not what is inside them.
    
    
    
  
    

  
    
    
    
      
    r4.smarthealthit.org
    
      
    When a server doesn't answer
    
    
    
    
    
      
    For most of the session SMART accepted the connection, completed TLS, and then sent nothing at all. The project kept going on HAPI alone, and the SMART numbers arrived once it recovered.
    
    
    
    
      
    
      
      
      What this changed in the code. One server failing no longer stops the run, failed requests are never cached, and FHIRLEARN_SERVERS=hapi skips a server that is down.

      Limitations
      
    
      
    
        
      
      • A snapshot, not a live view. Everything here was fetched on  and is embedded in the page. To refresh it, delete cache/, rerun the step modules (capability, compare, weird) and then python -m fhirlearn.report. Some parts will not update on their own: the five weird records are picked by hand and the build stops if one has been deleted, the weirdness probes compare birth dates against 2026-11-10, and the outage timeline and some captions describe this one session.
        • 
      
      • Test data. Both servers hold synthetic or demo records. Nothing here describes real patients or real prevalence.
        • 
      
      • Samples, not totals. Neither server returned Bundle.total, and the 20-page cap stops a search at 1,000 results.
        • 
      
      • The data moves. HAPI appears to be wiped and reloaded from time to time, and people write to it constantly. A fresh run will give different numbers.
        • 
      
      • One code per concept. Diabetes is matched only on SNOMED 44054006 and HbA1c only on LOINC 4548-4. Records coded only in ICD-10, with other HbA1c codes, or only in free text are missed.
        • 
      
      • Simple cleaning. % and percent are accepted, mmol/mol is converted with % = 0.09148 × mmol/mol + 2.152, and % values outside 3 to 20 are excluded rather than corrected.
        • 
      
      • "Patients sampled" is one page. It is the first 50 patients each server returned, not a random sample.
